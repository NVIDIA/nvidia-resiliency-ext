# L1 Semantic Analysis

L1 asks a configured model to interpret the current attempt. It receives the
bounded L0B view, may use declared read-only evidence tools, and returns a
structured primary when the initiating failure is visible, an independent
structured account of non-primary failure surfaces, plus root-cause and
recovery assessments.

L1 does not compare attempt history or choose `STOP` / `RESTART`.
`SCHEMA.md` owns the exact response shape, `TOOLS.md` owns tool APIs, and
`CONFIGURATION.md` owns route/provider settings.

L1 ends at the model's current-attempt semantic assessment and execution
record; source grounding, history comparison, and action policy belong to
L2-L4.

## Purpose And Authority

```text
L0ModelFacingView
  + generated response schema
  + static semantic contract
  + optional advertised tools
  + model route and deadline
  -> model interaction
  -> L1EvidenceResult
```

L1 is authoritative for preserving:

- the model's selected primary and causal role;
- the model's non-primary observed failures and optional selected observation,
  whether or not a primary is present;
- semantic failure identity and root-cause assessment;
- current-attempt failure domain and retry outlook;
- related failure roles and cited evidence;
- the raw provider response, model/tool turns, parsing state, and execution
  health.

L1 output is a model opinion under a closed advertised contract. Missing
required fields, invalid known-field types or enums, and contradictory
status/primary shapes make the result contract-invalid. Unknown fields do not:
the L1 boundary strips them from the semantic payload and records one
`unknown_response_fields_ignored` advisory containing their field paths. This
keeps provider extensions and unsolicited policy fields from reaching later
stages without discarding otherwise usable semantics. A renamed field still
fails when it leaves its required canonical field missing.

Formatting and output-efficiency deviations remain usable. Preferred
collection sizes, preferred identifier length, duplicate object IDs,
duplicate or dangling citation references, an unresolved or ambiguous selected
observation ID, missing primary/root-cause support tags, and non-canonical
no-primary placeholder prose or confidence produce L1 contract advisories.
The exact model response remains available in raw output and the interaction
trace; the normalized semantic payload contains only advertised fields. These
findings do not request contract repair or degrade the route. Observation
`evidence_ids` must still be non-empty
string arrays, but duplicate or dangling citation references are audited rather
than rejected because L2 independently grounds the selected observation line.
An unresolved or multiply resolved selected ID makes only the observation
track unavailable; it does not erase a usable primary or recovery assessment.
Missing recovery-claim support tags likewise remain an L2 observational
finding. After primary grounding, L4 applies the typed L1 values and statuses
to retry-rule selection. When the primary is absent but a selected observation
is grounded, L4 may use the assessment only for the root-independent general
rule; primary-dependent semantic rules remain unavailable.

The public response preserves the canonical parsed semantic object under
`l1_assessment`: advertised fields retain their model-provided values, while
unknown fields are omitted at the L1 boundary. No downstream stage mutates that
block. L2 findings, grounding resolutions, normalized failure facts, and
history identity are published separately under `l2_grounding`.

L0 candidates and causal-role hints are retrieval aids rather than semantic
truth. L1 owns their disambiguation and may select a different visible primary.
The result records whether L1 selected an `initiating` primary or could only
assign `unknown`; a known cascade or teardown cannot be the L1 primary.

## Inputs And Outputs

| Direction | Contract | Meaning |
| --- | --- | --- |
| Input | `L1EvidenceContext` | Immutable L0B view plus route-advertised read-only tools bound to L0A/source snapshot. |
| Input | `ModelRoute` and deadline | Endpoint, model, credentials, generation controls, tool policy, request timeout, and remaining analysis time. |
| Output | `L1EvidenceResult` | Provider-neutral execution status, transcript, calls, errors, usage, and parsed semantic payload. |
| Semantic payload | `restart_agent_evidence.v1` | Closed structured model response validated by `L1ResponseContract`. |

The semantic payload contains:

- `analysis_status`;
- `primary_failure`;
- `observed_failures` and `selected_observed_failure_id`;
- `root_cause_assessment`;
- `model_recovery_assessment`;
- `related_failures`;
- canonical `evidence` citations.

The executable `L1ResponseContract` generates both the model-visible response
schema and the client validator. The advertised and enforced contract therefore
has one source of truth.

## Semantic Task

L1 identifies:

1. the initiating observed failure when the log supports one, after considering
   complete traceback and chronological context;
2. the visible non-primary failure surfaces and at most one selected
   observation that best represents the terminal failure surface without
   asserting causality, independently of whether a primary was found;
3. a concise semantic failure identity: operation, mechanism, component,
   direct failure object path, and enclosing affected artifact path when
   visible;
4. root-cause status:
   `established_by_current_log`, `supported_but_unconfirmed`,
   `hypothesis_only`, or `unknown`;
5. exactly two recovery claims:
   - `failure_domain`: `workload`, `infrastructure`, or `unknown`;
   - `retry_outlook_without_workload_change`: `cannot_recover`, `may_recover`,
     or `unknown`;
6. per-claim evidence status and confidence;
7. downstream cascade, teardown, and unknown related failures when a primary
   exists;
8. visible line-and-quote citations tagged to the claims they support.

For `primary_identified`, canonical evidence must collectively support
`primary_failure` and `root_cause_assessment`. Support tags for substantive
`failure_domain` and `retry_outlook_without_workload_change` claims are
expected but are evaluated independently by L2. Their omission does not erase
a grounded primary or affected entity. A claim whose value and status are both
`unknown` is an abstention and does not require a positive supporting citation;
its rationale instead explains which evidence is missing.

`failure_identity.direct_failure_object_path` identifies the exact path on
which the failing operation directly acted. It may be an internal lock,
metadata, manifest, index, cache, shard, or temporary file.
`failure_identity.affected_artifact_path` separately identifies the runtime
artifact targeted by the enclosing workload operation. Either field may be
null independently. For example, a dataset-cache permission failure may name
the cache lock as the direct failure object and the dataset as the affected
artifact. A source-code location such as `file=/src/permute.cu, line=535,
call=cudaGetLastError()` is provenance and populates neither field.

If the initiating failure is absent but failure surfaces are visible, L1
returns `insufficient_evidence`, leaves `primary_failure` null, preserves those
surfaces in `observed_failures`, and may select one by id. A selected observation
must have causal role `unknown`, `cascade`, or `teardown`; it is not a substitute
primary. `related_failures` remains empty because no relationship to a primary
can be established.

The selected observation follows the same non-causal ordering used by L0A:
exclude retry-pending/recovered/progressed-after and diagnostic-only evidence,
prefer the terminal episode after the last applicable progress, collapse rank
fanout, and select the canonical first source occurrence of the strongest
remaining normalized group. If independent candidates remain equally
plausible, L1 leaves `selected_observed_failure_id` null and reports the bounded
candidate list. It does not relabel an observation to manufacture a primary.

When a primary exists, known causal relationships should normally use
`related_failures`. Additional or redundant `observed_failures` are tolerated
and remain independently auditable; their presence does not invalidate the
primary. Recovery claims describe the primary whenever one exists. The
observation track is then fallback evidence, not a second recovery opinion.

`no_failure_observed` remains distinct: it has no primary, no observed failures,
no selected observation, and no substantive recovery assessment.

Failure domain and retry outlook are independent. A workload fault may recover
after process recreation; an infrastructure fault may recur. Confidence is
semantic self-confidence for calibration, not an action score or L4 threshold.
Confidence MUST be interpreted with the enclosing `analysis_status`; it has no
standalone meaning.
A substantive claim is calibration eligible when its primary or selected
observation anchor is grounded. Primary/root accuracy and observation-only
recovery accuracy are scored separately. Claims whose value/status are both
`unknown` are excluded from confidence calibration and measured as abstentions.
The required `confidence=1` values in `no_failure_observed` remain contract
placeholders, not 1-percent model estimates.

## Declared Cluster Execution Context

L1 receives one canonical rendering of the typed, immutable
`ClusterExecutionContext` product contract:

```json
{
  "allocation_model": "homogeneous_node_pool",
  "workload_isolation": "exclusive",
  "replacement_hardware_bom": "equivalent",
  "replacement_software_bom": "equivalent",
  "replacement_resource_capacity": "equivalent",
  "replacement_resource_limits": "unchanged",
  "replacement_storage_access": "equivalent",
  "dependency_paths": [
    "compute_node",
    "scale_up_fabric",
    "scale_out_fabric",
    "distributed_storage",
    "service_control"
  ],
  "faulty_resource_handling": "independent_detection_and_quarantine"
}
```

The contract means that a workload allocation is drawn from a homogeneous
node pool and its resource envelope is invariant across eligible replacement
nodes. Workload code, data, configuration, and workload-selected software
remain unchanged. Workload identity, credentials, environment, configured
paths, and persistent filesystem permissions also remain unchanged across
restart; operator or administrator remediation is not part of the restart
transition. Failed processes are recreated; normal restart delay occurs; and
ephemeral process, node-local runtime, or external-service state may change. A
separate health mechanism may identify and quarantine malfunctioning nodes or
devices.

The dependency paths are functional categories, not hardcoded vendor or
deployment names. For example, a deployment may implement scale-up fabric with
NVLink/NVSwitch, scale-out fabric with InfiniBand or RoCE, and distributed
storage with Lustre. Those implementation examples belong in documentation and
evaluation fixtures rather than the production prompt.

The model assesses recovery in the next NVRx cycle under those guarantees.
Durable remediation and long-term preventive advice are outside the current
recovery assessment.

These are immutable product guarantees and belong in the static prompt, not in
configuration or per-request evidence. They describe the restart transition
and do not by themselves establish failure cause, ownership, or successful
recovery. Physical replacement does not imply changed capacity, resource
limits, workload demand, data, configuration, or software behavior.

A competing cause is relevant when the failed operation depends on the named
dependency path and that cause can produce the observed mechanism. Exact
physical-component identification is unnecessary. Merely knowing that a
component exists, or that hardware, services, and workload code can fail, is
not evidence. When supported workload and infrastructure alternatives remain,
L1 reports `failure_domain=unknown`; it independently reports whether the
restart transition could address the observed mechanism. Thus
`failure_domain=unknown` may validly pair with
`retry_outlook_without_workload_change=may_recover`. Independent quarantine is
a recovery mechanism only for a relevant malfunction; node replacement does
not imply repair of a persistent fabric, storage, or service fault. Retry
budgets and history are not shown to L1.

L1 reports `cannot_recover` when the observed failure is determined by
unchanged workload inputs and no supported restart transition can address it.
Exact root cause may remain unconfirmed; a theoretical transient unsupported by
the log does not by itself make the retry outlook `unknown`.

## Prompt Contract

The static system prompt owns stable task semantics:

- analyze one distributed-training attempt;
- separate observed mechanism, root cause, and recovery assessment;
- identify the initiating failure rather than tail noise;
- treat application/model/data/configuration and workload-selected framework
  behavior as workload-domain only when supported;
- avoid inferring ownership or persistence of mutable resources from call stack
  or missing cleanup text;
- preserve uncertainty when one log cannot distinguish persistent failure from
  retry recovery;
- separate cascade and teardown from the primary;
- cite only visible evidence;
- return JSON only, without long chain-of-thought.

The user message is one machine-readable per-invocation envelope. It contains:

- the static generated `response_schema`;
- request-specific deterministic `failure_narrative`;
- request-specific compact `decision_evidence_view`;
- request-specific `attempt_execution_context`;
- request-specific `evidence_bundle`.

The schema is generated from the executable L1 contract and transported in the
invocation envelope; it is not dynamic evidence. L1 owns this envelope
assembly. L0B supplies only `failure_narrative`, `decision_evidence_view`,
`attempt_execution_context`, and `evidence_bundle` through
`L0ModelFacingView.prompt_payload()`.

It does not repeat static behavioral rules, route configuration, tool schemas,
history, retry budgets, source-log location components, or eval labels.
Workload artifact paths observed in log content remain evidence and may appear
in `decision_evidence_view` or `evidence_bundle`.

Failure-family examples do not accumulate in the static prompt. They belong in
deterministic registries/taxonomy, eval gold, or versioned prompt experiments
whose corpus-level benefit is measured.

## Optional Tool Loop

L1 always starts from L0B. If the selected route advertises tools, the model may
request the generic read-only interfaces in `TOOLS.md`.

Tools are a context escape hatch, not another policy path:

- tool availability and turn limits are route-configured;
- zero configured tool rounds resolves to one tools-disabled model turn;
- production-fidelity eval uses the same advertised tool shape;
- unknown or unadvertised calls are rejected and traced;
- each turn replays the conversation because the OpenAI-compatible API is
  stateless at this contract boundary;
- every request is clamped to the smaller of route timeout and remaining
  whole-analysis deadline;
- reaching the turn cap triggers one forced no-tool final evidence response;
  contract-valid evidence remains usable, while absent or invalid final
  evidence makes L1 unusable and leaves the deterministic recommendation
  authoritative.

## Usability And Degradation

`L1ExecutionAssessment` is the single execution-health contract consumed by
tracing, route publication, and downstream stages. It separately records route
lifecycle, result quality, parse status, evidence presence, and closed reason
codes. `SCHEMA.md` owns its exact fields and enums.

An L1 semantic payload is `usable` when:

- the route finishes before the whole-analysis deadline;
- no provider timeout or output truncation invalidated the response;
- extraction succeeded with one parsed semantic payload;
- the object passes the hard structural, enum, and semantic-consistency
  requirements of `L1ResponseContract`.

Earlier retryable HTTP failures, provider retries, unsupported tool requests, or
a tool-round limit followed by valid forced-final evidence mark a usable route
`degraded`; a successful contract-repair turn is also degraded because the
first response was not contract usable. These conditions do not erase valid
semantics. L1 contract advisories and L2 audit findings do not make L1
unusable. Contract advisories are retained in the L1 anomalies, interaction
trace, and public result-provenance notes.

L1 permits at most one additional tools-disabled final-evidence turn. Its closed
reason distinguishes three cases:

| Final-turn reason | Trigger |
| --- | --- |
| `contract_repair` | The previous response was missing, malformed, non-object, or contract-invalid JSON. |
| `forced_final_after_tool_exhaustion` | The configured tool-round budget ended without a semantic response. |
| `forced_final_after_output_limit` | The previous model response ended with `finish_reason=length`. |

The additional turn may use configured provider HTTP retries, but it cannot
request tools and is never followed by another semantic repair/final turn. A
provider failure or whole-analysis deadline does not trigger this turn.

`L1ExecutionAssessment.final_evidence_reason` preserves the applicable value
independently of `reason_codes`: the former explains why the additional turn
ran, while the latter records whether execution quality was degraded. L2 and
L4 do not use either field as semantic or policy evidence.

A final provider timeout, output truncation, missing/unparseable JSON, or
structurally contract-invalid output makes L1 unusable. Missing primary,
root-cause, or recovery support tags are not reasons for a contract-repair
turn. Unknown non-empty evidence support tags are retained in the model output,
ignored for claim-support accounting, and reported as contract advisories; a
malformed `supports` value remains invalid. A structurally valid final response
remains usable and proceeds to L2, which independently grounds the selected
line and records citation gaps as observational findings. One recovered tool
exhaustion or prior output limit makes the route usable-but-degraded and
preserves the exact final-turn reason.
L1 failure never invalidates the already available deterministic
recommendation.

Once a final turn is selected, `final_evidence_reason` records why it was
selected even if the analysis deadline prevents provider dispatch or the turn
later fails at the provider boundary. `unusable_reason` independently records
the provider or deadline failure that made the result unusable.

Parsing accepts an unambiguous JSON object embedded in prose or a Markdown code
fence and falls back to safe Python-literal decoding for common formatting
variations. A second top-level JSON object is ambiguous and triggers the one
permitted contract-repair turn rather than silently selecting the first. It
does not invent missing syntax. A syntax failure records both
the strict JSON location and the fallback-parser error. A decoded value that
violates the closed response contract is instead `contract_invalid`; the trace
retains the parsed object and the individual contract violations.

A final timeout or truncation remains unusable even if a partial payload could
be parsed. Conversely, a prior failed provider attempt does not make a later
contract-valid response unusable. The typed assessment applies this precedence;
consumers do not infer status from raw anomaly fields.

Non-primary statuses remain bounded:

- `no_failure_observed` has no primary, no observed failure, and unknown
  recovery claims;
- `insufficient_evidence` has no primary and explicit missing evidence. It may
  retain observed failures and a substantive recovery claim only when exactly
  one selected observation and its support citations satisfy the response
  contract. Without that selected anchor, its recovery claims remain unknown.

This preserves a visible terminal failure surface without presenting it as an
initiating cause. `SCHEMA.md` defines the advertised canonical placeholder
strings, their advisory acceptance behavior, and the hard selected-observation
constraints enforced by `L1ResponseContract`.

## Provider And Context Safety

The client:

- uses an OpenAI-compatible `/chat/completions` route;
- explicitly requests non-streaming responses with `stream=false`;
- reuses one persistent synchronous `httpx` connection pool per model route;
- applies configured or built-in model context-window limits before every turn;
- reserves a safety margin and reduces only that turn's output cap when needed;
- rejects a turn before HTTP as non-retryable `context_budget_exceeded` when
  estimated input plus the safety reserve leaves no response capacity;
- traces requested and effective output caps;
- retries only configured transient provider failures;
- classifies HTTP, connect, read, write, protocol, and timeout failures into
  stable trace categories;
- distinguishes provider retry from model contract repair;
- distinguishes client context preflight from provider context-window
  rejection;
- does not log credentials or expose long chain-of-thought;
- returns at the whole-analysis deadline without waiting for abandoned workers.

The HTTP client performs transport and connection-pool work only. Restart Agent
owns retry count and backoff, whole-analysis deadline enforcement, provider
response parsing, tool-loop state, and observability. Runtime shutdown closes
route-owned pools; caller-injected HTTP clients retain caller ownership.

Context preflight resolves its cap from explicit route configuration first,
then the built-in model-limit table. For an unknown model with no configured
cap, preflight still estimates and traces input size but does not reject the
request or reduce its output cap; the provider remains authoritative and any
reported context rejection is classified as `context_window_exceeded`.

Provider retryability is closed and deterministic:

| Provider outcome | Trace category | Retried when budget remains |
| --- | --- | --- |
| Recognized provider context-window rejection in an HTTP error or 2xx error envelope | `context_window_exceeded` | no |
| HTTP `429` or `500`-`599` | `http_error` | yes |
| Other HTTP `4xx` | `http_error` | no |
| HTTPX connect/read/write/pool timeout while analysis time remains | `timeout` | yes |
| HTTP request exhausts the absolute whole-analysis deadline | `analysis_deadline_exceeded` | no provider retry |
| Connect, read, write, close, proxy, or remote-protocol failure | corresponding stable transport category | yes |
| Provider response is not valid JSON | `provider_response_decode_error` | yes |
| Local-protocol, unsupported-protocol, or HTTPX response-decoding failure | corresponding stable transport category | no |
| Unclassified HTTPX request failure | `request_error` | no |
| Client context preflight or whole-analysis deadline exhaustion | `context_budget_exceeded` or `analysis_deadline_exceeded` | no provider retry |

HTTPX timeouts keep the stable `error_type=timeout` classification and add
`timeout_kind=connect|pool|write|read|unknown` for diagnosis. A
deadline-clamped HTTP timeout retains the same diagnostic subtype while its
authoritative failure remains `analysis_deadline_exceeded` and is not counted
as an endpoint issue.

The `openai_compatible` module's `_is_retryable_http_status` and
`_httpx_request_error` classifiers, together with its explicit timeout and
provider-JSON handlers, are the executable classification source. `max_retries`
limits only provider retries; the remaining whole-analysis deadline may
prevent a classified retry from starting.

Invalid JSON is handled according to which contract failed:

| Failure | Meaning | Handling |
| --- | --- | --- |
| `provider_response_decode_error` | The complete HTTP response body is not valid provider API JSON. | Retry the provider request within the same logical model turn, subject to provider retry and deadline limits. |
| `contract_repair` | The provider response is valid, but the assistant content is malformed or violates the L1 response contract. | Use the one permitted tools-disabled final-evidence turn. |

A provider retry does not consume the model-facing `contract_repair` turn.

L1 accepts only one complete JSON provider response per model turn. It does not
process streamed chunks, retain partial model output after an interrupted
response, or treat partial content as semantic evidence. An interrupted read is
classified as a timeout or transport failure; a complete body that is not valid
JSON is classified as `provider_response_decode_error`. A tool result still
requires a subsequent stateless HTTP request containing the prior conversation
and that result.

Multiple routes may execute concurrently after shared L0. Each route produces
an independent L1-L4 candidate; the current `collect_all` mode does not
arbitrate among them.

## Tracing

L1 tracing preserves:

- exact static and dynamic prompt payloads;
- advertised tool schemas;
- resolved model-route options;
- every model request and visible response;
- every tool request and result;
- any final-evidence turn and its closed reason;
- provider attempts, HTTP/provider errors, retries, and timeouts;
- token usage and finish reasons;
- context-budget calculations;
- contract parsing and repair;
- the complete final `L1ExecutionAssessment`.

Credentials, auth headers, and bearer tokens are never recorded.

## Service Logging

L1 emits one INFO completion event per configured route:

```text
event=restart_agent.l1.completed route_id=<id> model=<model>
execution_status=<status> usable=<bool> wall_clock_s=<seconds>
model_wall_clock_s=<seconds> tool_wall_clock_s=<seconds>
model_calls=<count> tool_calls=<count> failed_calls=<count>
retries=<count> endpoint_issues=<count> total_tokens=<count>
```

An unusable or provider-failed route uses WARNING with the same fields plus a
bounded error classification. DEBUG emits one
`restart_agent.l1.model_call.completed` or
`restart_agent.l1.tool_call.completed` event per call with call index,
latency, success, retry scheduling, finish reason, token counts, tool name,
and whether new context was returned. Prompts, responses, arguments, tool
output, endpoint credentials, and API keys remain trace-only.

`endpoint_issues` counts transport timeouts that occur while analysis time
remains, HTTP failures, and provider-response decode failures. A request whose
deadline-clamped timeout exhausts the whole-analysis budget is
`analysis_deadline_exceeded`, not a provider endpoint issue. Context-window
exhaustion and model response-contract failures likewise do not inflate
endpoint reliability failures.

## KPIs

L1 has three distinct measurement families.

### Semantic Quality

| KPI | Example |
| --- | --- |
| Primary/mechanism accuracy | Gold primary is checkpoint metadata decode; L1 selects the corresponding line and mechanism rather than the later Python wrapper. |
| Primary-abstention accuracy | When the initiating cause is absent, L1 leaves `primary_failure=null` rather than relabeling a TCPStore peer symptom as initiating. |
| Observed-failure selection accuracy | With repeated peer-disconnect copies, L1 selects the canonical grounded failure surface and excludes retry-pending warnings. |
| Root-cause status accuracy | One failed read with plausible corruption and transient alternatives is `supported_but_unconfirmed`, not established. |
| Recovery-field accuracy | Domain and retry outlook independently match reviewer gold. |
| Citation quality | Every claim has visible, correctly tagged source support. |
| Calibration | Among substantive `primary_identified` claims, cases reported near 80 confidence are correct at approximately that rate over the corpus; abstention placeholders are excluded. |

### Behavioral Efficiency

| KPI | Example |
| --- | --- |
| First-turn usable-result rate | Valid evidence is returned from L0B without tools. |
| Extra model turns | Two tool rounds and one final answer add two extra turns beyond the initial call. |
| Useful tool yield | A complete tool scan finds normalized evidence groups absent from L0B. |
| Duplicate/no-new tool rate | `initial_view_overlap.new_evidence_beyond_initial_view=false`; the query only rediscovered lines, occurrence groups, or incidents already represented in L0B. |
| Token and latency efficiency | Semantic correctness is achieved with fewer turns, tokens, and wall time. |

### Endpoint Reliability

| KPI | Example |
| --- | --- |
| Request success rate | Completed provider responses divided by attempted requests. |
| Retry/timeout/error rate | Transient 502, timeout, and retry counts remain separate from semantic failures. |
| Total downstream API time | Wall time spent awaiting all provider calls, including queueing and model service work visible to the client. |
| Deadline hit rate | A usable route result arrives before the configured analysis deadline. |

Model quality, behavioral efficiency, and endpoint reliability are reported
separately before a combined route recommendation is made.
